## CSAPP Cache Lab Part B：矩阵转置优化与学习感想

> 从最初的简单分块，到分析 Cache Set 冲突，再到利用 B 矩阵暂存数据。这次实验让我逐渐理解：Cache 优化的核心并不是减少访问次数，而是让数据在被驱逐之前得到充分利用。

## 一、实验背景

完成 Cache Lab Part A 后，我开始进行 Part B 的矩阵转置优化。

Part A 主要是实现一个 Cache Simulator，通过模拟 Cache 的映射、替换和访问过程，统计 Hit、Miss 和 Eviction。

Part B 则有所不同。

这一次不再是模拟 Cache，而是需要利用已经学过的 Cache 知识，优化矩阵转置程序，尽可能减少 Cache Miss。

矩阵转置的基本操作很简单：

```c
B[j][i] = A[i][j];
```

但真正开始优化后，我才发现，一个看起来只有两层循环的程序，背后涉及很多问题：

- Cache Line 的大小与数据排列方式；
- 矩阵的行优先存储；
- 空间局部性与时间局部性；
- 直接映射 Cache 的 Set 冲突；
- 不同矩阵尺寸对 Cache 映射的影响；
- 数据访问顺序和 Cache Line 的生命周期。

实验需要优化三种矩阵：

1. 32×32
2. 64×64
3. 61×67

实验采用的 Cache 参数为：

| 参数 | 数值 | 含义 |
| --- | --- | --- |
| s | 5 | 32 个 Cache Set |
| E | 1 | 每个 Set 只有一条 Cache Line |
| b | 5 | 每条 Cache Line 为 32 Bytes |
| Cache 容量 | 1024 Bytes | 32×1×32 |

由于 `int` 占用 4 Bytes，因此一条 Cache Line 能容纳：

\[
32 / 4 = 8 \text{ 个 int}
\]

这一点是后面所有优化的重要基础。

---

## 二、最开始的想法：利用分块改善局部性

最开始，我的思路非常直接。

既然矩阵转置时，A 是按行读取、B 是按列写入，那么 B 的空间局部性会很差。

因此可以使用分块（Blocking）的方法，将一个大矩阵拆成多个小矩阵，限制每次访问的数据范围。

例如：

```c
for (i = 0; i < N; i += 8) {
    for (j = 0; j < M; j += 8) {
        for (k = i; k < i + 8; k++) {
            for (l = j; l < j + 8; l++) {
                B[l][k] = A[k][l];
            }
        }
    }
}
```

这里的代码只是展示基本分块思想，实际实现还需要处理矩阵边界。

### 为什么选择 8×8？

当时的理解是：

一条 Cache Line 可以存储 8 个整数，因此使用 8×8 分块，似乎就能够充分利用 Cache Line。

实际测试也证明，分块确实有效。

在 32×32 矩阵中，普通转置大约产生 1184 次 Miss，而简单的 8×8 分块将 Miss 降到了 346 次。

这让我第一次直观地感受到空间局部性对程序性能的影响。

不过，这个阶段我的理解仍然比较简单：

**我认为只要分块大小与 Cache Line 的大小匹配，性能就应该比较好。**

后面的 64×64 实验证明，这个想法并不完整。

---

## 三、32×32：第一次遇到 A 和 B 的 Cache 冲突

在 32×32 矩阵中，每一行有 32 个整数，因此占用：

\[
32\times4=128\text{ Bytes}
\]

每行跨越 4 个 Cache Block。

对于行起点，映射的 Set 编号每次相差 4。

如果从 Set 0 开始，那么连续 8 行的起始 Cache Line 分别映射到：

```text
第 0 行：Set 0
第 1 行：Set 4
第 2 行：Set 8
第 3 行：Set 12
第 4 行：Set 16
第 5 行：Set 20
第 6 行：Set 24
第 7 行：Set 28
```

这意味着连续 8 行对应的 Cache Line 可以映射到不同的 Set，不会因为它们彼此之间的映射而发生冲突。

但仍然存在另一个问题：

**A 和 B 是两个不同的矩阵，却可能映射到相同的 Cache Set。**

例如，在首地址映射对齐的假设下：

```text
A[0][0] -> Set 0
B[0][0] -> Set 0
```

由于实验采用直接映射 Cache，每个 Set 只能容纳一条 Cache Line。

当 A 的数据刚刚被读取，随后访问 B 的对应位置时，A 的 Cache Line 就可能立即被驱逐。

这种问题在对角线分块中尤其明显。

### 延迟写入对角线元素

为了减少冲突，我尝试了延迟写入对角线元素的方法。

大致思路是：

先将对角线元素保存到局部变量中，处理完其他元素后，再写入 B。

经过调整，我最终将 32×32 的 Miss 降到了约 288 次，达到了实验的性能目标。

这让我认识到：

**Cache 优化不仅与访问了哪些数据有关，还与访问这些数据的先后顺序有关。**

即使两段程序完成完全相同的矩阵转置，只要读写顺序不同，Cache Miss 就可能不同。

## 四、64×64：为什么相同的 8×8 分块不再有效？

这是整个实验中让我困惑最多的部分。

最开始，我认为 32×32 使用 8×8 分块能够取得不错的性能，那么 64×64 应该也可以继续使用。

但实际结果并不理想。

后来我尝试了 4×4 分块，Miss 大约为 1700 次，仍然高于 1300 次的满分要求。

一开始，我不理解为什么同样的分块思想，在 64×64 中表现差了这么多。

后来重新计算 Cache Set 的映射，才逐渐理解原因。

### 1. 64×64 的 Set 映射规律

64×64 矩阵每行包含 64 个整数，占用：

\[
64\times4=256\text{ Bytes}
\]

一行相当于 8 条 Cache Line。

因此相邻行对应位置的 Cache Set 编号相差 8。

假设起始位置映射到 Set 0：

```text
第 0 行：Set 0
第 1 行：Set 8
第 2 行：Set 16
第 3 行：Set 24
第 4 行：Set 0
第 5 行：Set 8
第 6 行：Set 16
第 7 行：Set 24
```

可以发现，每隔 4 行就会映射到相同的 Set。

例如：

```text
B[0][0] -> Set 0
B[4][0] -> Set 0
```

这两个元素属于不同的 Cache Line，但映射到相同的 Cache Set。

如果连续访问它们，就可能互相驱逐。

**64×64 的问题在于，它不仅存在 A、B 之间的冲突，B 自己的不同数据行之间也会产生明显的冲突。**

这也是为什么简单的 8×8 分块不再那么有效。

### 2. 从 8×8 改成四个 4×4 子块

为了解决这个问题，我尝试将一个 8×8 分块进一步拆成四个 4×4 子块：

```text
A 矩阵：

┌──────────┬──────────┐
│          │          │
│  左上    │  右上    │
│          │          │
├──────────┼──────────┤
│          │          │
│  左下    │  右下    │
│          │          │
└──────────┴──────────┘
```

但由于矩阵转置的特性，A 中的右上角会转置到 B 的左下角，A 中的左下角则会转置到 B 的右上角。

也就是说：

```text
A：                   B：

┌──────┬──────┐      ┌──────┬──────┐
│  ①  │  ②  │      │  ①  │  ③  │
├──────┼──────┤  ->  ├──────┼──────┤
│  ③  │  ④  │      │  ②  │  ④  │
└──────┴──────┘      └──────┴──────┘
```

我尝试了不同的子块处理顺序，发现 Miss 可能相差数百次。

其中一种顺序能够将 Miss 降到约 1400 次。

这时，我开始产生一个疑问：

如果 B 的第 0 行与第 4 行会发生冲突，那么我是不是应该尽量先把 B 的前四行处理完，再处理后四行？

这个方向有一定道理，但后来我发现自己忽略了 A。

### 3. 不能只分析 B，还必须同时考虑 A

矩阵转置涉及两种访问：

```text
读取 A
    ↓
写入 B
```

如果只分析 B 的 Cache Set，而忽略读取 A 时可能造成的驱逐，那么分析是不完整的。

例如：

```text
读取 A[1] -> 驱逐 B[1]
写入 B[1] -> 驱逐 A[1]
```

这意味着，某个 B 的 Cache Line 本来可以复用，但中间读取 A 的操作可能把它驱逐。

同样，A 的 Cache Line 也可能因为写 B 而被提前驱逐。

因此，分块顺序的选择实际上存在一种取舍：

- A 希望按行连续读取。
- B 希望按行连续写入。
- 两者的访问方向却因为转置而相反。

这也是我当时越分析越困惑的原因。

对于很小的 Cache 示例，我可以手动计算每次 Hit、Miss 和 Eviction。

但当矩阵变成 64×64，涉及 A、B 两个矩阵、多个分块以及不同访问顺序时，单纯依靠脑子模拟整个 Cache 的状态已经非常困难。

后来我意识到，不应该试图一次分析整个矩阵，而应该先固定一个 8×8 分块，逐步分析其中的数据访问和 Cache Set 映射。

## 五、64×64 的关键优化：利用 B 矩阵暂存数据

这是整个实验中让我印象最深的一种优化方法。

之前的算法主要是在调整 4×4 子块的处理顺序。

但后来尝试了一种不同的思路：

**不立即将数据写入 B 的最终位置，而是先利用 B 的部分空间暂存数据，之后再交换到正确位置。**

### 1. 第一步：一次读取 A 的 8 个元素

```c
a0 = A[k][j];
a1 = A[k][j + 1];
a2 = A[k][j + 2];
a3 = A[k][j + 3];

a4 = A[k][j + 4];
a5 = A[k][j + 5];
a6 = A[k][j + 6];
a7 = A[k][j + 7];
```

由于 A 是行优先存储，而且当前处理的是按 8 对齐的分块，因此这 8 个连续整数恰好属于同一条 Cache Line。

这样做有一个明显的好处：

**即使这条 Cache Line 之后被 B 驱逐，我们也不需要再次读取它，因为需要的 8 个整数已经全部保存到局部变量中。**

相比之下，之前的 4×4 算法可能只读取 A 一行的前 4 个元素，之后 Cache Line 被驱逐，等到读取后 4 个元素时又需要重新加载。

### 2. 第二步：借用 B 的空闲位置

正常转置应该将 A 右上角的数据写入 B 左下角。

但为了避免过早访问 B 后四行，可以暂时把这些数据放到 B 右上角。

随后，在处理 A 左下角时：

1. 读取 A 左下角的数据。
2. 取出暂存在 B 右上角的数据。
3. 将 A 左下角写到 B 右上角。
4. 将暂存数据写到 B 左下角。

最后再处理 A 右下角。

整个过程可以表示为：

```text
第一步：

B：
┌──────────┬──────────┐
│ A左上转置│ A右上暂存│
├──────────┼──────────┤
│          │          │
└──────────┴──────────┘


第二步：

B：
┌──────────┬──────────┐
│ A左上转置│ A左下转置│
├──────────┼──────────┤
│ A右上转置│          │
└──────────┴──────────┘


第三步：

B：
┌──────────┬──────────┐
│ A左上转置│ A左下转置│
├──────────┼──────────┤
│ A右上转置│ A右下转置│
└──────────┴──────────┘
```

通过这种方式，64×64 的 Miss 可以进一步降低到约 1100～1200 的水平。

### 3. 我当时最大的疑问：为什么增加读写次数，反而减少了 Miss？

刚看到这种算法时，我其实很不理解。

因为暂存数据需要额外的写入，之后还需要将数据读取出来并搬运到正确位置。

这意味着程序执行了更多内存访问。

我最开始认为：

既然读写次数增加了，那么 Miss 应该也会增加才对。

后来才发现，这里混淆了两个概念：

**内存访问次数不等于 Cache Miss 次数。**

例如：

```text
读取 B[0][4]：Hit
读取 B[0][5]：Hit
读取 B[0][6]：Hit
读取 B[0][7]：Hit
```

虽然发生了 4 次读取，但如果对应的 Cache Line 已经在 Cache 中，并且中途没有被驱逐，那么这些访问不会产生新的 Miss。

与此同时，新算法可能避免了某些 A Cache Line 的重复加载。

因此，即使总访问次数增加，Cache Miss 仍然可能减少。

这让我对局部性有了新的理解：

**优化并不是让程序尽可能少地访问数据，而是让每次加载进来的数据得到尽可能充分的利用。**

## 六、进一步思考：Eviction 并不一定意味着额外的损失

在分析 64×64 的过程中，我还有一个很重要的认识转变。

最开始，我总是希望避免 Cache Eviction。

因为我认为只要发生驱逐，程序性能就一定会变差。

后来才发现，这种理解不够准确。

假设一条 Cache Line 包含：

```text
A[0][0] A[0][1] A[0][2] A[0][3]
A[0][4] A[0][5] A[0][6] A[0][7]
```

存在两种情况。

### 情况一：数据还没用完，就被驱逐

```text
加载 A[0][0..7]
       ↓
只使用前 4 个元素
       ↓
被 B 驱逐
       ↓
之后需要使用后 4 个元素
       ↓
重新加载，产生 Miss
```

这种驱逐造成了后续的重复加载。

### 情况二：数据已经全部使用，再被驱逐

```text
加载 A[0][0..7]
       ↓
使用全部 8 个元素
       ↓
被 B 驱逐
       ↓
后续不再访问这条 Cache Line
```

这种情况下，虽然发生了 Eviction，但由于后面不再需要这条数据，因此不会因为它被驱逐而再次产生 Miss。

需要注意，触发驱逐的那次访问本身仍然是 Miss。

真正可以避免的是将来对被驱逐数据的重复加载。

这让我意识到：

**Cache 优化的重点并不只是减少驱逐，而是尽量减少仍然有用的数据被提前驱逐。**

换句话说，应该尽量在一条 Cache Line 被驱逐之前，完成对其中数据的使用。

## 七、64×64 的进一步优化与取舍

当算法已经能够达到约 1176 Miss 的水平时，我们开始考虑是否还能够进一步优化。

64×64 包含：

\[
64\times64=4096
\]

个整数。

由于一条 Cache Line 能够容纳 8 个整数，因此 A、B 各包含 512 条 Cache Line。

如果每条 Cache Line 都只需要加载一次，那么理想情况下：

\[
512+512=1024\text{ Miss}
\]

这个数值可以作为当前模型下的一个理论参考下界。

假设实际产生 1176 次 Miss，则额外 Miss 为：

\[
1176-1024=152
\]

这些额外 Miss 可能来自 A、B 的相互冲突、B 不同行之间的冲突，以及尚未使用完的 Cache Line 被提前驱逐。

我们也尝试讨论了一些微调方向：

- 改变右下角 4×4 子块的访问顺序；
- 调换第二步中读取 A 和 B 的顺序；
- 调整第二步的两组写入顺序；
- 针对对角线分块进行特殊处理；
- 提前读取 A 右下角的数据。

但这些修改并不保证一定更好。

例如，先读取 B 中暂存的数据，表面上似乎可以避免 B 被 A 驱逐。

但之后读取 A 时，又可能把刚刚访问的 B Cache Line 驱逐，导致接下来写 B 时重新产生 Miss。

因此，不能简单地认为某一种访问顺序永远更优。

更重要的是，我逐渐意识到一个工程上的问题：

**性能优化应该有边界。**

当程序已经达到实验要求，而且算法结构比较清晰时，为了减少少量 Miss 而继续增加大量特殊情况，未必值得。

最终，我决定保留现有的 8×8 + 4×4 + B 暂存交换算法，而不是继续进行过度优化。

## 八、61×67：分块大小为什么不是越整齐越好？

相比 64×64，61×67 的问题又有所不同。

一开始，我采用了一个比较简单粗暴的方案：

先处理能够完整划分的 56×56 区域，再使用普通转置处理剩余部分。

但实际结果约为 2392 Miss，没有达到 2000 以下的满分目标。

后来，我尝试直接对整个矩阵进行分块，并在循环中处理边界：

```c
for (i = 0; i < N; i += 16) {
    for (j = 0; j < M; j += 16) {
        for (k = i; k < i + 16 && k < N; k++) {
            for (l = j; l < j + 16 && l < M; l++) {
                B[l][k] = A[k][l];
            }
        }
    }
}
```

这种方式不再需要把剩余区域单独留给普通转置。

### 1. 为什么 17×17 比 16×16 更好？

在实验中，我发现了一个有趣的现象：

16×16 的 Miss 较高，而 17×17 反而最低；继续增加到 18×18、19×19，Miss 又有所上升，但并没有立即回到 16×16 的水平。

这个变化让我感觉 Cache Miss 和分块大小之间似乎存在一种波浪式关系。

后来我理解了，这种现象并不意味着存在固定的周期规律。

它反映的是不同分块尺寸改变了 Cache Set 的映射情况和数据复用时机。

61×67 与 64×64 不同。

A 的每行有 61 个整数：

\[
61\times4=244\text{ Bytes}
\]

B 的每行有 67 个整数：

\[
67\times4=268\text{ Bytes}
\]

它们都不是 32 Bytes 的整数倍。

因此，相邻行的起点并不会总是落在固定间隔的 Cache Set 上。

不同分块大小会改变分块边界、访问的数据范围以及冲突发生的时机。

所以，17×17 恰好取得更低 Miss，并不是因为 17 这个数字本身具有某种特殊性质。

**分块大小与 Cache Miss 之间通常是非单调关系，不能仅凭直觉判断。**

### 2. 为什么矩形分块也可能优于正方形分块？

后来我尝试了矩形分块。

例如：

```text
17×8：A 的 17 行、8 列
8×17：A 的 8 行、17 列
```

实验发现，17×8 的 Miss 更低。

这让我意识到一个以前没有考虑过的问题：

**矩阵转置中的 A 和 B，其实并不具有对称的访问需求。**

A 希望按行连续读取。

B 也希望按行连续写入。

但是 A 的行会变成 B 的列。

因此，一个在 A 中是 17 行、8 列的分块，转置到 B 后就变成 8 行、17 列。

这会改变 B 每一行能够连续处理的数据数量，以及相关 Cache Line 被重复访问的时机。

也就是说，分块不一定要使用正方形。

矩形分块可以通过调整高度和宽度，在 A 的读取局部性与 B 的写入局部性之间寻找更好的平衡。

### 3. 交换循环顺序，Miss 又减少了约 100 次

原来的代码是：

```c
for (k = i; k < i + blockH && k < N; k++) {
    for (l = j; l < j + blockW && l < M; l++) {
        B[l][k] = A[k][l];
    }
}
```

这种方式优先保证 A 的连续读取。

但如果交换两个内层循环：

```c
for (l = j; l < j + blockW && l < M; l++) {
    for (k = i; k < i + blockH && k < N; k++) {
        B[l][k] = A[k][l];
    }
}
```

就变成优先保证 B 连续写入。

实际实验中，我发现这样做又能够减少约 100 次 Miss。

这让我进一步认识到：

对于矩阵转置，不能只关心 A 的空间局部性。

有时候牺牲一部分 A 的读取局部性，换取 B 更好的写入局部性，反而能够减少总 Miss。

不过，只知道总 Miss 下降，并不能直接证明减少的部分全部来自 B。

要进一步确认原因，还需要分别统计 A 的读 Miss 和 B 的写 Miss。

## 九、整个实验过程中，我的理解是怎样变化的？

回顾整个 Part B，我觉得自己的认识经历了几个阶段。

### 第一阶段：认为分块就是优化

最初，我认为矩阵转置只需要将大矩阵拆成多个小矩阵。

只要分块足够小，并且与 Cache Line 大小匹配，性能就应该提高。

后来发现，分块只是第一步。

### 第二阶段：开始考虑 Cache Set 冲突

在 64×64 中，我发现即使采用 8×8 分块，性能仍然不理想。

通过计算 Set Index，我才理解：

不同内存地址可能映射到相同的 Cache Set。

尤其在直接映射 Cache 中，两个不同 Cache Line 只要映射到同一个 Set，就无法同时存在。

这让我开始从地址映射的角度分析程序。

### 第三阶段：意识到不能只分析一个矩阵

最开始，我主要关注 B 的写入。

但 A 的读取同样会改变 Cache 的状态，甚至驱逐 B 中原本能够复用的数据。

因此，分析矩阵转置时，必须同时考虑 A 和 B。

这一步让我感到最困难。

因为问题从简单的单个 Cache Line，变成了两个矩阵之间复杂的相互影响。

### 第四阶段：从避免 Miss，转向充分利用 Cache Line

使用 B 矩阵暂存数据的算法让我认识到：

即使增加内存访问次数，也可能减少 Cache Miss。

真正重要的是数据的访问顺序，以及每条 Cache Line 在被驱逐之前是否已经完成需要的工作。

这是我认为整个实验中最重要的理解转变。

### 第五阶段：认识到实验和分析需要结合

很多优化在逻辑上似乎很合理，但实际结果可能正好相反。

例如：

- 更大的分块不一定更好；
- 16×16 不一定比 17×17 好；
- 正方形分块不一定比矩形分块好；
- 先读取 B 的暂存数据不一定减少 Miss；
- 减少读写次数不一定减少 Cache Miss。

因此，优化不能完全依赖直觉。

正确的方法应该是：

提出假设 → 修改一个变量 → 运行实验 → 对比 Miss → 分析原因。

如果同时修改多个地方，即使 Miss 降低了，也很难判断真正起作用的是哪项修改。

## 十、学习感想与总结

这次 Cache Lab Part B 给我最大的感受是：**理解 Cache 的基本原理，与真正利用这些原理优化程序，是两件不同的事情。**

在 Part A 中，我已经能够实现 Cache Simulator，也知道什么是 Hit、Miss、Eviction、LRU，以及直接映射和组相联 Cache 的区别。

对于几个简单的地址访问，我可以手动计算 Cache 的状态变化。

所以最初开始 Part B 时，我认为自己已经比较熟悉 Cache 的工作方式。

但真正分析 64×64 矩阵时，我还是感到非常困难。

因为一次矩阵转置涉及成千上万次读写操作，A 和 B 又可能不断驱逐彼此的数据。即使知道每次访问会映射到哪个 Set，也很难仅靠直觉判断整个程序的 Miss 数量。

后来我逐渐意识到，自己不应该试图在脑中模拟整个矩阵，而应该先将问题缩小到一个 8×8 分块，再进一步分析其中的 4×4 子块。

通过这种方式，我才慢慢理解为什么有些访问顺序能够减少冲突，为什么有些数据需要暂存，以及为什么某些看似多余的内存访问反而能够提高 Cache 性能。

我认为这次实验最重要的收获有三个。

**第一，Cache 优化关注的不只是数据在哪里，还包括数据什么时候被访问。**

两个程序即使访问相同的数据，只要访问顺序不同，就可能产生完全不同的 Cache Miss。

**第二，Cache Line 被驱逐并不可怕，可怕的是它还没有被充分利用，就不得不在之后重新加载。**

因此，应该尽量让加载到 Cache 中的数据在被驱逐之前完成更多有用的工作。

**第三，性能优化需要在复杂度与收益之间取得平衡。**

在 64×64 的优化中，我们已经找到了比较有效的 8×8 + 4×4 暂存交换算法。虽然理论上还有继续降低 Miss 的空间，但进一步优化可能需要更加复杂的数据调度与特殊处理。

对于当前的学习目标来说，理解已有算法为什么有效，比单纯追求更低的 Miss 数量更重要。

另外，在 61×67 的实验中，我也发现分块大小并不存在一种固定的最佳选择。矩阵尺寸、Cache 参数、数据对齐方式以及访问顺序都会影响最终结果。

这使我开始理解，性能优化往往没有一个可以直接套用的万能公式。

我们需要先理解硬件和程序之间的关系，再通过实验去验证自己的假设。

### 最后的思考

如果要用一句话总结这次实验，我会写：

> **Cache 优化不是让数据永远留在 Cache 中，而是让数据在有限的停留时间里发挥最大的价值。**

从最初的简单分块，到研究 Cache Set 冲突，再到通过局部变量和 B 矩阵暂存数据，我逐渐从“只知道 Cache 的工作原理”，走向“能够根据 Cache 的工作方式思考程序应该怎样访问内存”。

虽然距离真正掌握高性能程序优化还有很长的路，但这次实验让我第一次比较深入地体会到：程序的执行效率，不仅取决于算法做了多少工作，也取决于这些工作是以什么顺序完成的。

这也是学习计算机系统知识最有意思的地方——原本看起来很抽象的硬件机制，最终能够直接影响我们写出的每一段代码。
